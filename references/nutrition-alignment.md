# 营养对齐与套餐拆解

这是整个 skill 里最容易算出假数据的一环。下面每条都有实测数字撑着。

## 一、先看这张表，决定要不要拆套餐

单店（`1950739`，19:00 正餐）实测：

| 路径 | 命中率 | 说明 |
|---|---|---|
| 单点 SKU 名称直接查营养表 | **18/109 = 16.5%** | 菜单里大量是 `可乐`、`雪碧`、`薯条` 这种通用名，营养表里是 `可乐中杯`、`雪碧中杯`、`中薯条` |
| 套餐拆解后子项查营养表 | **34/39 = 87.2%** | 因为 `query-meal-detail` 返回的子项名是带规格的完整名 |

**结论：想要可信热量，必须拆套餐。** 舍不得 20 次只读调用，就等着 83% 的 SKU 没数据。

拆完后整体覆盖约 45%-50%，剩下的是周边（丝巾、水手帽）、当季新品（龙焰、月堡）、以及没有对应营养条目的组合类商品。

## 二、四层对齐（按顺序，命中即停）

```
L0  精确        NFKC + 去空白 + 小写后完全相等
L0.5 去连字符   麦辣鸡翅2块 ↔ 麦辣鸡翅-2块
L1  规格后缀    苹果片 ← 苹果片一袋(60g)      （营养表名是菜单名的前缀，剩余部分只是规格）
L1b 反向规格    纯牛奶 ← 纯牛奶(盒装)          （菜单名是营养表名的前缀）
L2  份数折算    麦辣鸡翅4块 = 麦辣鸡翅-2块 × 2 （必须留 note 说明折算依据）
```

「规格」的判定：剩余部分去掉量词后只剩数字/字母/单位（`60g`、`(盒装)`、`大杯`）。
实现见 `scripts/nutrition_solver.py:_rest_is_spec`。

## 三、三种必须拒绝的情况

### 1. 通用名歧义 —— 拒绝，别猜

```
可乐   → 可乐中杯(147) / 可乐大杯(224) / 可乐小杯(107)   猜错就是 100 kcal
雪碧   → 雪碧中杯(105) / 雪碧大杯(160) / 雪碧小杯(76)
薯条   → 中薯条(289) / 大薯条(379) / 小薯条(210) / 迷你薯条(106)
```

`solve()` 会返回 `None`，`ambiguous_options()` 给出候选。上层要拿这个候选去**问用户**（或干脆改用套餐拆解后的完整名），不能自己挑一个。

### 2. 套餐名 ≠ 主品名 —— 拒绝

`麦香鱼套餐` 不能退化成 `麦香鱼`（325 kcal）。真实套餐是 761 kcal（麦香鱼 + 中薯条 + 可乐中杯），退化成主品等于漏掉 436 kcal。

同理 `牛气满满套餐` 不能退化成 `牛气满满`。营养表里虽然有 `牛气满满` 这条，但**无法确证它代表整个套餐还是主品** —— 不确定就不猜。

### 3. 风味变体 —— 拒绝

`那么大鸡排（椒盐风味）` ≠ `那么大鸡排`。风味不同、热量未必相同，不猜。

## 四、套餐拆解规则

```python
rounds[].choices[] 里取 quantity > 0 的子项
```

- 用 `quantity` 而不是 `isDefault`：12 个套餐实测两者一致（0 处分歧），但 `quantity` 语义上就是"已选数量"，更稳
- `rounds[].id` 是数字，回传 `calculate-price` 时要转字符串
- 任一子项查不到营养 → 整体标 `combo_partial`，**不进控卡求解**。热量必然偏低，拿它算"≤700kcal"是在骗人
- 聚合后的营养必须标 `matched_by = "combo_decomposed"`（组合方案则标 `aggregate`），不许冒充 `exact`

实测验证：麦香鱼套餐 = 325 + 289 + 147 = **761 kcal**，蛋白 16+4+0 = **20g**，钠 556+165+0 = **721mg**。

## 五、缺失数据的处理

| 情况 | 处理 |
|---|---|
| `energyKcal` 为 null 但 `energyKj` 有值 | `round(kJ × 0.239, 1)` 兜底，note 注明 |
| 整个营养条目不存在 | `kcal = None` + `matched_by = "unknown"`，**绝不写 0** |
| 份数不同（4块 vs 2块） | 按比例折算，note 写明「按 N 倍折算」 |
| 套餐部分子项缺失 | `combo_partial`，控卡场景排除；非控卡场景可进解但要降权 |
| 营养表重名（实测 2 条） | 取首条并在报告里 warnings 出来 |

**`None` 参与除法、参与求和、被当成 0 —— 这一条错了，后面全错。**

### 非控卡场景的例外（2026-10-23 补）

用户只给预算、不给热量目标时，`combo_partial` 不该被一刀切排除 —— 否则会出现
「30 元 3 人早餐只有油条可选」这种荒谬结果（实测成因：早餐组合全都配「鲜萃冰咖」，
而它在营养表里没有，于是全部早餐组合被判不完整）。

但放宽要有底线，三条同时成立才放行：

1. 至少有一项真实营养（`kcal` 不为 None 且 > 0）；**0 kcal 的方案一律不进解**，卡片上写 0 等于骗人
2. 打分乘 0.85 降权，不能凭「缺数据导致偏低的热量」压过数据完整的方案（实测「精选超值随心配」缺主品，只剩 351 kcal/蛋白 0g，曾是靠低价排到第一）
3. 卡片上必须注明缺的是哪一项，例：`火腿扒麦满分组合：缺营养数据：鲜萃冰咖`

### 已知的营养表空洞（早餐时段尤其严重）

| 商品 | 状态 | 影响 |
|---|---|---|
| 吉士蛋麦满分 | **未收录** | 早餐主力汉堡，整个套餐只能算出配食的热量 |
| 鲜萃冰咖 | **未收录** | 几乎所有早餐「组合」的默认配饮，导致组合集体变成 `combo_partial` |
| 粥王系列 | 未收录 | 粥类无热量数据 |
| 可乐麦炫酷 | 未收录 | 随心配粉区默认选项 |

遇到这些不要找相似商品替代 —— 铁律 4 不允许。写「营养表未收录」，或换用户能接受的等价子项后重新算价。
