# 门店定位规则（`query-nearby-stores`）

> 只记 MCP 工具文档没写、或者说错的部分。参数语义与返回字段直接读工具 schema，这里不复制。
> 证据矩阵见本文件末尾，30+ 组参数实调。

## 五条硬事实

| 事实 | 证据 |
|---|---|
| **`city` 是业务城市硬围栏，不是行政区** | `city=保定`+`keyword=容城` → 0 家；`city=雄安`+`keyword=容城` → 2 家。容城行政属保定，业务归雄安 |
| **`city` 与 `keyword` 必须同时非空** | 缺一即 `600058`；文案「城市名或者关键词不能为空」是字面意思，不是二选一 |
| **`keyword` 在围栏内做 POI 解析，且会静默降级** | `city=容城县`+`keyword=国贸`（在北京）→ 不报错，返回雄安 2 家 |
| **`distance` 不可信** | 同一家店 570m ↔ 7574m，随 keyword 变化 13 倍 |
| **单次最多 5 家，无分页** | 北京国贸 / 上海人广 / 保定市区均恰好 5 家 |

`city` 不需要后缀：`保定` = `保定市`，`雄安` = `雄安新区`。三套门店库（到店自取 `beType=1`、得来速 `beType=5`、外送 `delivery-query-stores`）的 `storeCode` 不通用。

## 错误码 → 真实归因

| code | 真实含义 | 修法 |
|---|---|---|
| `600014` | `keyword` 在该 city 围栏内解析不到地址 | 换成本城市内的 POI |
| `600047` | 解析成功，但该点周边无门店 | **换 city**（业务城市，不是上级市） |
| `600050` | `searchType` 用了默认值 1（搜收藏） | 显式传 `2` |
| `600058` | `city` / `keyword` 缺一个 | 两个都补 |
| `600057` | 门店已打烊 | 换 `businessStatus == true` 的门店，或改预约 |

`600014` 与 `600047` 必须分清：前者是"这地方解析不到"，后者是"地方找到了但没店"。修法相反。

## 降级顺序

1. 换 POI（本城市内确定存在的地标）
2. **换 city**（业务城市）—— 失败最常见的原因，新区 / 开发区 / 跨行政边界尤甚
3. 换 `beType=5` 试得来速（独立门店库）
4. 走外送库 `delivery-query-stores`（第三套库，需 `addressId`）
5. 以上全空，才说「无门店」，并说清是哪一套库

## 对用户的话怎么说

- 说「只有 N 家」**只在 N < 5 时成立**；返回 5 家只能说「最近的 5 家」
- **不要拿 `distance` 说"离你 300 米"** —— 它是 keyword 解析点到门店的直线距离，与用户真实位置无关
- 返回有店 ≠ 关键词命中。门店名对不上用户说的地方时，要主动说明"系统按城市中心兜底了"

## 证据矩阵

### `city` 围栏

| city | keyword | 结果 |
|---|---|---|
| `容城县` | `容城` | ✅ 2 家（雄安） |
| `雄安` / `雄安新区` | `容城` | ✅ 2 家 |
| `保定` / `保定市` | `容城` / `容城县` | ❌ `600047` 0 家 |
| `北京市` | `容城` | ❌ `600014` |
| `保定` | `北京国贸` | ❌ `600014` |
| `保定` | `麦当劳` | ✅ 5 家（保定市区） |

容城 / 雄县 / 安新行政上属保定，业务城市归**雄安**。写错 city 的表现是「附近没有餐厅」，不是报错 —— 最易误判成"这里没店"。

### `distance` 随 keyword 漂移（同一家店 `1950401`）

| keyword | distance |
|---|---|
| 商务服务中心 | 570 m |
| 容东 | 994 m |
| 白洋淀 | 3966 m |
| 启动区 | 4776 m |
| 安新 | 5946 m |
| 大王 | 7574 m |

门店不变，距离差 13 倍 → `distance` 是「解析点 → 门店」，与用户位置无关。

### 已确认门店（雄安，到店自取 `beType=1`）

| storeCode | 门店名 | 营业时间 | 备注 |
|---|---|---|---|
| `1950739` | 麦当劳保定雄安容东盛容荟购物广场餐厅 | 07:00-23:00 | 支持预约 |
| `1950401` | 麦当劳保定雄安新区奥威东路餐厅 | 07:00-22:00 | 支持预约 |

雄安无得来速门店，最近在保定白沟（约 14km，`beType=5` 库）。

### 静默降级的完整案例（2026-10-22 复现）

```
city=保定, keyword=商务服务中心  →  返回 3 家，全在【涿州】
  1950880 麦当劳涿州范阳西路(新)餐厅        2728 m
  1950603 麦当劳涿州京深路水岸花城得来速餐厅  6010 m
  1950424 麦当劳涿州范阳东路得来速餐厅       7319 m
```

用户想找的是雄安市民服务中心旁的店，系统在保定围栏里解析成了涿州。
**接口不报错、有数据返回、门店名完全对不上** —— 这是最容易把用户带偏的失败模式。

所以拿到结果后必须核对一条：**门店名/地址里是否出现用户说的那个地标**。对不上就是降级了，换 city 重查。

## 自查

- [ ] `city` 是业务城市，不是上级行政区
- [ ] 门店名对得上用户说的地方（keyword 可能降级，不能盲信）
- [ ] 说「只有 N 家」时 N < 5
- [ ] 没拿 `distance` 当真实距离

## 补充实测（2026-10-22）

### `city` 填「容城县」有效，「雄安」不是必要的

用户说「雄安」时，`city=雄安` 不一定通；填**县级行政区**「容城县」实测正常返回 2 家：

```
city=容城县, keyword=奥威  →  1950401 奥威东路店（地址：奥威东路雄安市民服务中心H301室）
                              1950739 容东盛容荟店（地址：容东乐安北2街178号盛蓉荟一层）
```

`keyword` 传「奥威」和传「容东」返回**同样的 2 家**——说明 keyword 只做粗筛，
别指望它精确命中；真正判断靠门店名/地址文字比对。

### 返回体是**数组**，不是 `{"stores": [...]}`

`query-nearby-stores` 的 `data` 直接就是 list。按 `data.get("stores")` 取会抛
`'list' object has no attribute 'get'`。`delivery-query-stores` 同理。

### 建地址时门牌会被地理编码改写

`delivery-create-address(address="<城市><道路>", addressDetail="<门牌>")`
返回的 `fullAddress` 不是两者的简单拼接，系统会先补全道路门牌、拼上邻接地标：

```
<省><市><区><道路>57号 <邻接地标><用户写的门牌>
```

实测把「XX路」补全成了「XX路57号 <邻接地标>」，再拼上用户写的门牌，结果和用户说的门牌对不上。

**建完必须把 `fullAddress` 念给用户确认**，不能默认解析对了——它可能落到了隔壁楼。
